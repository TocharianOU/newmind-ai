# SaaS 计价与计费最终共识

本文件用于记录当前最新的 SaaS 计价、计费、会员、余额、模型、工具调用与 Stripe 实践方案。

目标：

- 统一旧方案与新方案，避免继续沿用已经过时的“梯队额度包”思路
- 明确 `BASE / PRO`、美元余额、自动扣款、模型计价、工具计价之间的关系
- 为后续产品、后端、Billing 页面与数据模型改造提供统一依据

---

## 1. 最终结论

当前最终共识如下：

1. `PRO` 月费采用信用卡自动续费订阅模式。
2. `BASE` 继续保留免费试用定位，不强制绑卡。
3. 平台变量成本不再主推“token 包 + A/B/C 梯队次数包”售卖。
4. 平台变量成本统一收敛为“美元余额（USD balance / credit balance）”扣费。
5. 模型调用按 token 规则折算后，从美元余额中扣费。
6. 工具调用按“每个工具自己的单价”直接从美元余额中扣费。
7. 仍然保留 `A / B / C / X` 梯队，但主要作为内部运营、成本分层、默认定价模板与风控分类，不作为用户主要购买对象。
8. 用户不需要理解复杂的次数包体系，用户看到的是：
   - 套餐订阅
   - 当前美元余额
   - 每个工具单次价格
   - 模型使用的扣费规则
9. 后续可以增加“低余额自动补充（auto top-up）”，但不建议做“每次调用直接刷卡一次”的实时逐笔扣卡。

一句话总结：

`PRO 自动订阅 + 美元余额扣费 + 可选自动补充`，是当前推荐的最终 SaaS 付费模式。

---

## 2. 为什么放弃旧的“额度包”主方案

最初方案偏向：

- `BASE / PRO` 附带月度 token
- 额外购买 token 包
- 额外购买 `A / B / C` 梯队次数包
- `1 次工具调用 = 1 次梯队额度`

这个方案的优点是容易快速上线，但缺点也很明显：

1. 用户需要理解 token 包、工具次数包、梯队包，概念较多。
2. 对欧美 SaaS 用户来说，体验不如“订阅 + 余额”直观。
3. 工具成本未来可能分化明显，继续用统一梯队包会限制定价灵活性。
4. SKU 会越来越多，Billing 页面会越来越复杂。
5. 财务视角不如美元余额统一，难以把模型和工具计费放进同一个账户视图。

因此，旧方案不再作为主要商业方案，只保留其中“梯队分类”的内部价值。

## 3. 旧方案与新方案的关系

### 3.1 最初的想法

最初主要思路：

- 模型侧：`BASE / PRO` 附送月 token，超出后买 token 包
- 工具侧：按 `A / B / C / X` 分梯队，订阅内送每月调用次数，超出后买梯队调用包
- 对外售卖对象：
  - token 包
  - A/B/C 次数包

### 3.2 现在的最终想法

现在主要思路：

- 模型侧：仍保留月赠送 token 作为订阅体验额度
- 工具侧：仍保留部分月赠送能力或试用额度，但不再作为主要售卖逻辑
- 对外售卖对象改为：
  - `PRO` 订阅
  - 美元余额充值
  - 可选自动补充

### 3.3 什么保留，什么淘汰

保留：

- `BASE / PRO` 两档订阅结构
- `medium-agent / strong-agent` 的能力分层
- `A / B / C / X` 梯队的内部分类价值
- 月赠送额度的体验设计

淘汰或降级为“内部参考”：

- 面向用户主售的 token 包体系
- 面向用户主售的 A/B/C 梯队次数包体系
- “用户买的是梯队额度包”这种表述

## 4. 当前推荐的对外产品结构

### 4.1 `BASE`

定位：

- 免费试用与轻度使用者
- 不要求绑定信用卡即可开始体验
- 提供有限但真实可感知的产品价值

建议：

- 月费：`$0`
- 可用模型：`medium-agent`
- 每月赠送 token：`2M`
- `strong-agent`：不开放
- 自定义模型：不开放
- 部分平台工具可提供少量免费体验额度或赠送 credit
- 用完后引导升级 `PRO` 或充值余额

### 4.2 `PRO`

定位：

- 正式用户的最低付费门槛
- 通过自动续费订阅获得稳定收入
- 以“完整能力 + 一定月赠送额度”作为核心卖点

建议：

- 月费：延续当前 `PRO` 建议值
- 计费方式：Stripe 订阅自动续费
- 可用模型：`medium-agent`、`strong-agent`
- 每月赠送 token：`5M`
- 自定义模型：开放
- 工具调用：可有少量订阅内赠送额度，但超出后按美元余额扣费

## 5. 美元余额模式

### 5.1 核心定义

平台新增用户级美元余额概念，例如：

- `usdBalance`
- 或命名为 `creditBalanceUsd`

该余额用于承担所有变量成本：

- 模型调用
- 平台托管工具调用
- 未来其他按量资源

### 5.2 用户看到的内容

用户侧只需要理解：

1. 我当前是什么套餐
2. 我每月有多少赠送额度
3. 我的美元余额还有多少
4. 我每次调用某个工具会扣多少钱
5. 我的模型使用会如何消耗余额

### 5.3 用户充值方式

建议充值档位：

- `$10`
- `$25`
- `$50`
- `$100`

这类充值是一次性支付，不是订阅。

### 5.4 自动补充

后续建议增加：

- 用户可开启 auto top-up
- 例如余额低于 `$5` 时，自动充值 `$20`

这比“每次工具调用直接刷卡”更稳健，原因：

- 降低支付通道开销
- 减少高频小额扣款失败
- 账单更清晰
- 风控更容易

## 6. 模型计价规则

### 6.1 模型能力层

继续保留：

- `medium-agent`
- `strong-agent`

用户前端只看到产品能力名称，不直接暴露上游真实模型品牌与供应商细节。

### 6.2 计价原则

模型侧仍然保留“产品 token”概念，用于：

- 月赠送额度的消耗
- 强弱模型的差异化扣费
- 用户体验与产品包装

当前建议继续使用：

- `medium-agent = 1x`
- `strong-agent = 3x`

即：

- 实际 raw tokens 先记录到账务和审计中
- 产品 token 用倍率折算
- 月赠送额度先消耗产品 token

### 6.3 月赠送额度与余额的关系

推荐顺序：

1. 优先消耗订阅附带的月赠送 token
2. 月赠送 token 用完后，再从美元余额扣费

这样可以保持：

- `BASE / PRO` 仍然具有明显的“订阅价值”
- 高频成本继续由按量付费承担

### 6.4 美元扣费口径

美元扣费建议不要直接把上游账单原样暴露给用户，而是保留产品层转换：

- 对内：按真实 input / output / cache 成本核算
- 对外：以简化的产品单价或折算规则收费

这样可以保留：

- 运维成本空间
- 支付手续费空间
- 滥用与波动缓冲
- 商业保密性

---

## 7. 工具计价规则

## 7.1 对外规则

工具计价不再以“梯队包”作为主要用户购买对象。

改为：

- 每个工具有自己的单次价格
- 每次调用直接从美元余额扣费

例如：

- `VirusTotal: $X / call`
- `Shodan: $Y / call`
- `AbuseIPDB: $Z / call`

### 7.2 对内规则

`A / B / C / X` 仍然保留，但作用改变为：

1. 内部成本分层
2. 默认价格模板
3. 风控与额度策略
4. 新工具快速归类
5. BI / 报表统计

因此，梯队仍然有价值，但不再是用户主要购买对象。

### 7.3 `X` 梯队

`X` 继续表示：

- `BYOK`
- 自定义集成
- 用户自带地址/凭据的系统
- 平台不承担第三方商业 API 成本的集成

这类调用通常：

- 不按平台工具单价扣费
- 或只收取极低的平台服务费
- 或仅消耗模型 / 平台代理相关资源

最终具体是否收费，可按产品策略单独决定。

### 7.4 是否还保留赠送工具额度

可以保留，但定义应简化为：

- `BASE / PRO` 可附带少量免费工具调用额度或工具 credit
- 超出后统一走美元余额扣费

不再强调：

- 购买 `A: 50 calls`
- 购买 `B: 200 calls`
- 购买 `C: 1000 calls`

## 8. Stripe 实践建议

### 8.1 Stripe 中的对象拆分

建议拆成三类：

1. `Subscription`
   - `PRO monthly`
   - 可扩展 `PRO yearly`

2. `One-time payment`
   - 购买美元余额充值档位

3. `Optional auto top-up rule`
   - 不是单独商品，而是平台逻辑
   - 当余额低于阈值时，自动创建一次固定金额的 Payment Intent / Checkout

### 8.2 不建议的方式

当前不建议：

- 每次模型请求都直接触发一次信用卡扣费
- 每次工具调用都直接创建一次 Stripe 小额支付

原因：

- 支付开销高
- 工程复杂
- 对账难
- 失败与拒付处理复杂
- 用户账单体验差

## 9. 数据模型与实现建议

### 9.1 订阅

保留现有订阅体系：

- `Subscription`
- `planName`
- `stripeCustomerId`
- `stripeSubscriptionId`

### 9.2 新增余额账务模型

建议新增：

- `User.usdBalance`
- `BalanceTransaction`

`BalanceTransaction` 建议字段：

- `id`
- `userId`
- `type`
  - `topup`
  - `auto_topup`
  - `model_charge`
  - `tool_charge`
  - `refund`
  - `manual_adjustment`
- `amountUsd`
- `balanceBefore`
- `balanceAfter`
- `referenceType`
  - `subscription`
  - `usage_record`
  - `tool_usage_record`
  - `payment`
- `referenceId`
- `metadata`
- `createdAt`

### 9.3 模型侧落地

继续保留：

- `UsageRecord`
- raw token 记录
- input/output/cost 记录

增加：

- 是否已从余额扣费
- 扣费金额
- 关联 `BalanceTransaction`

### 9.4 工具侧落地

继续保留：

- `ToolUsageRecord`

增加或配套：

- 每次调用的美元成本记录
- 实际对用户的扣费金额
- 关联 `BalanceTransaction`

## 10. Admin 与用户界面建议

### 10.1 Billing 页面

用户侧重点展示：

- 当前套餐
- 下次订阅扣款时间
- 本月赠送 token 剩余
- 当前美元余额
- 充值入口
- 是否开启自动补充
- 每个工具单价

### 10.2 Dashboard

建议展示：

- 月赠送 token 已用 / 剩余
- 美元余额变化
- 最近模型费用
- 最近工具费用
- 工具使用排行榜

### 10.3 Admin

建议展示：

- 每个工具单价配置
- 每个梯队默认价格模板
- 用户余额与最近账务变动
- 毛利观察
- 高成本工具告警

## 12. 后续实践路径

建议按以下顺序推进：

### Phase 1

- 保留当前 `BASE / PRO`
- 保留月赠送 token 逻辑
- 新增美元余额账户
- 工具改为支持“单工具单价”
- 模型与工具都能从余额扣费

### Phase 2

- Billing 页面改造为“订阅 + 余额 + 充值”
- 展示工具单价而不是梯队包
- 增加余额流水与费用明细

### Phase 3

- 增加 auto top-up
- 增加 Admin 定价后台
- 支持按环境变量或管理后台配置工具单价和模型计价参数

### Phase 4

- 视真实数据决定是否还保留少量工具免费额度
- 视真实成本决定是否对不同工具端点做差异定价
- 视风险决定是否对部分高成本工具增加单用户日限额或风控阈值

---

## 13. 最终建议

对外：

- 订阅卖权限和体验额度
- 余额承担持续变量成本
- 工具直接按单工具定价

对内：

- 保留梯队做分类、默认模板、风控和报表
- 不再把梯队包当成主要商业对象

这就是当前推荐的最终计费与定价体系。
