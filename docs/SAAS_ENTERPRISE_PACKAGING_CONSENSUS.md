# SaaS / Enterprise 套餐与能力共识

## 文档目的

本文档用于记录当前已经达成的产品与实现共识，范围包括：

- SaaS 订阅套餐
- Enterprise 私有化部署
- MCP 集成能力
- Hub Key / BYOK 策略
- 自定义集成
- 自定义模型

## 1. 产品线定义

- SaaS 套餐只保留 `BASE` 和 `PRO` 两档。
- `Enterprise` 不再作为普通 SaaS 自助订阅套餐存在。
- `Enterprise` 的含义统一为：私有化 / 自部署 / 企业交付模式。
- Hub 的 Billing 页面中，`Enterprise` 卡片保留，但不再走直接付费购买，而是跳转到 `Contact Sales` / `联系我们`。

## 2. 套餐定位

### `BASE`

- 提供基础聊天能力。
- 提供标准 MCP 集成能力。
- 可以使用一部分平台托管的高成本外部资源，但应有明确配额限制。
- 支持用户自己填写集成配置。
- 支持 `BYOK`（前提是该集成本身支持）。
- 支持用户自定义 / 自建集成。
- 不支持自定义模型提供商。
- 不支持填写自定义模型 API Key。

### `PRO`

- 包含 `BASE` 的全部能力。
- 支持高级集成。
- 对平台托管的高成本外部资源提供高配额，实际体验上可以接近“不限制”，但仍保留风控 / 滥用保护。
- 支持用户自己填写集成配置。
- 支持 `BYOK`（前提是该集成本身支持）。
- 支持用户自定义 / 自建集成。
- 支持自定义模型提供商。
- 支持填写自定义模型 API Key。

### `Enterprise` 私有化部署

- 表示私有化交付，不是 SaaS 中的一档普通套餐。
- 具有最高权限和最大灵活性。
- 支持 License、私有化部署控制、自定义模型等企业能力。
- 对于高成本第三方服务，优先建议客户使用自己的凭据、自己的代理服务，或者通过企业合同单独约定。

## 3. MCP 集成策略

当前共识是：

- 不再把“能安装多少个 MCP server”作为主要的套餐差异。
- 类似 `20 MCP servers`、`Unlimited MCP servers` 这种说法，不适合作为核心成本控制逻辑。
- 真正应该区分的是：
  - 是否能使用高成本集成
  - 是否能使用 `Hub Key`
  - 平台代付资源的调用额度
  - 是否支持 `BYOK`
  - 是否支持自定义集成

## 4. Hub Key / BYOK 共识

对于 `VirusTotal`、`Shodan`、`AbuseIPDB` 这类会产生平台真实成本的集成：

### `BASE`

- 可以使用 `Hub Key`
- 但只能给有限额度
- 如果集成支持 `BYOK`，用户也可以改为填写自己的 Key

### `PRO`

- 可以使用 `Hub Key`
- 给予高额度，接近不限制
- 如果集成支持 `BYOK`，用户也可以填写自己的 Key

### `Enterprise`

- 优先建议客户使用自己的凭据、自己的代理、或者专门约定的企业方案

## 4.1 基于当前已集成工具的价格梯队

当前共识不是做 `A/B/C` 方案，而是做 `A/B/C/X` **价格梯队**。

规则如下：

- 每个工具都归属于一个固定的价格梯队
- 用户购买的是订阅内自带的各梯队额度，或者额外购买某个梯队的额度包
- 新增工具时，优先做“归类到某个梯队”，而不是单独重新设计价格体系

### `A` 价格梯队

定位：

- 价值最高
- 平台资源最稀缺
- 默认次数最少
- 补充包价格最高

当前建议归属：

- `virustotal`

说明：

- 当前已具备可用的 VirusTotal 平台密钥能力
- 因此在 SaaS 设计中，`VirusTotal` 不再默认视为“仅 BYOK”能力
- 但仍应纳入最高价格梯队管理，避免被视为无限平台资源

### `B` 价格梯队

定位：

- 中等成本
- 有明确平台成本
- 适合做 `PRO` 的核心增值能力

当前建议归属：

- `shodan`

### `C` 价格梯队

定位：

- 低到中成本
- 最适合做平台托管的标准情报源能力
- 默认次数可以比 `A/B` 更宽松

当前建议归属：

- `abuseipdb`

### `X` 梯队（免费 / 自定义集成梯队）

定位：

- 平台通常不承担第三方 API 商业成本
- 主要是用户自己已有系统、自己提供地址、凭据或密钥
- 更接近“集成能力开放”，而不是“平台代付资源”

当前建议归属：

- `jira`
- `confluence`
- `splunk`
- `elasticsearch`
- `kibana`
- `cloudtrail`
- `cloudwatch`
- `aws-s3`
- `aws-iam`
- `aws-ec2`
- `aws-lambda`
- `aws-network`
- `aws-security`
- 用户自定义集成

说明：

- `X` 梯队可视为免费梯队 / 自定义集成梯队
- 这类集成通常不计入平台付费工具额度池
- 其主要成本来自产品研发、代理请求、模型消耗、运维和支持成本，而不是第三方 API 商业账单

## 4.2 工具额度与扣费规则

当前先只从“平台承担的外部工具成本”视角定义工具价格梯队，不考虑 Enterprise 单独模式。

### 用户购买方式

用户购买的不是“某个工具的独立方案”，而是：

1. 订阅内自带的各梯队额度
2. 额外购买某个梯队的额度包

例如：

- `BASE` 自带少量 `A/B/C` 梯队额度
- `PRO` 自带更多 `A/B/C` 梯队额度
- 如果某个梯队用完，可单独补充该梯队额度

### 当前统一扣费规则

第一阶段统一采用最简单规则：

- 每调用一次工具，扣减该工具所属梯队的一次额度

即：

- `1 次工具调用 = 1 次该梯队额度`

示例：

- 调用一次 `VirusTotal`，扣减 `A` 梯队 `1` 次
- 调用一次 `Shodan`，扣减 `B` 梯队 `1` 次
- 调用一次 `AbuseIPDB`，扣减 `C` 梯队 `1` 次

当前暂不区分：

- 不同工具不同权重
- 不同端点不同价格
- 不同请求复杂度不同扣减

后续只有在真实使用数据证明必要时，再升级成加权扣减模型。
  - 如果后续采购正式商业服务，再单独定义平台额度策略

## 5. 自定义集成共识

- `BASE` 支持自定义集成
- `PRO` 支持自定义集成
- 集成配置继续通过 `configSchema` 暴露给用户填写
- 只要某个集成本身支持 `BYOK`，那么在 `BASE` / `PRO` 下都应允许用户填写自己的配置

这意味着：  
“用户能不能自己配”不应该成为 `BASE` 和 `PRO` 的主要差异点；  
主要差异应该是“平台代付资源能给多少额度”。

## 6. 自定义模型共识

自定义模型只支持：

- `PRO`
- `Enterprise`

自定义模型不支持：

- `BASE`

这里的“不支持”包括：

- 不允许新增自定义模型提供商
- 不允许保存自定义模型 endpoint 信息
- 不允许填写自定义模型 API Key
- 不在 chat 模型选择器中暴露自定义模型

## 6.1 模型与工具的计费思路

当前共识：

- 模型成本和工具成本要分开设计
- 不建议把模型 token 和工具调用次数混成同一个池子

### A. 模型计费思路

当前底座模型假设为：

- `medium` = `Claude Sonnet 4.6`
- `strong` = `Claude Opus 4.6`

模型成本建议内部按加权方式核算，而不是直接对外暴露原始 token 单价。

现阶段建议：

- `medium` 作为基础模型能力
- `strong` 作为高成本模型能力
- 后续可以按 credits / token quota / weighted usage 的方式计费

### B. 工具计费思路

工具侧先采用最简单、最容易理解的方案：

- 每调用一次工具，记一次额度消耗

即：

- `1 次工具调用 = 1 次工具额度`

这个规则当前先统一适用于平台托管的高成本情报源工具。

后续如果有必要，再升级为加权模式（例如某些高成本工具一次调用扣 2 次或 3 次），但第一阶段不做复杂化。

### C. 当前推荐的计费结构

SaaS 侧建议拆成两部分：

1. 订阅费  
包含基础模型额度、基础功能权限、基础工具额度

2. 额外额度包  
当用户超过默认额度时，可以单独购买补充额度

### D. 额外额度包的方向

后续支持：

- 额外模型额度包
- 额外工具调用次数包

其中：

- 用户额外购买的模型额度，单独计费
- 用户额外购买的工具调用次数，也单独计费

### E. BYOK 对计费的影响

如果用户使用自己的 Key：

- 不应消耗平台托管工具额度
- 平台主要收取订阅费和产品能力费
- 第三方 API 成本由用户自己承担

## 7. Billing / 文案呈现共识

- Billing 页面继续保留 `Enterprise` 卡片
- 但 `Enterprise` 不再作为普通 SaaS 订阅购买
- `Enterprise` 卡片应该跳转到 `Contact Sales` / `联系我们`
- 不再把 `Unlimited MCP servers` 作为核心卖点
- 更适合强调：
  - 私有化部署
  - 高级集成
  - BYOK
  - 自定义模型
  - 企业支持 / SLA

## 8. 实现方向

后续实现应遵循以下规则：

- 移除 SaaS 体系中把 `ENTERPRISE` 当成普通套餐的逻辑
- 保留 Enterprise deployment mode 作为单独概念
- 自定义模型能力只允许 `PRO` 和 `Enterprise`
- 自定义集成与 `BYOK` 在 `BASE` / `PRO` 中都允许
- 对平台代付资源建立明确的额度控制
- 不再把 MCP server 数量作为主要成本控制方式
- 工具额度第一阶段统一采用 `每调用一次算一次`

## 9. 应改动的层级

为了真正落地这套共识，后续改动大致会分成下面几个层级：

### 9.1 产品与文案层

需要调整：

- Hub Billing 页面套餐文案
- Enterprise 卡片按钮行为
- MCP / 集成能力描述
- 自定义模型可用范围描述

对应位置通常包括：

- Hub 前端页面文案
- 多语言文案文件
- 官网 / 文档页面

### 9.2 前端展示层

需要调整：

- Billing 页面中 `BASE` / `PRO` / `Enterprise` 的展示逻辑
- 自定义模型入口的显示条件
- 用户在集成市场里看到的提示信息
- 如果后续做配额提示，还要在前端展示“Hub Key 剩余额度”或“当前受限说明”

### 9.3 Hub 后端权限层

需要调整：

- 套餐与功能权限映射
- 自定义模型接口的权限判断
- `BASE` 禁止保存 / 使用自定义模型
- `PRO` 与 `Enterprise` 允许自定义模型

### 9.4 Hub 后端计费 / 配额层

这是最关键的一层。

需要补充：

- 对高成本集成的 Hub Key 调用额度控制
- `BASE` 有限额度
- `PRO` 高额度
- `Enterprise` 走独立策略
- 第一阶段工具扣费规则统一为：`1 次调用 = 1 次额度`

推荐的控制维度：

- 按用户
- 按集成类型
- 按时间窗口（日 / 月）
- 区分 `Hub Key` 与 `BYOK`

第一阶段建议优先记录：

- 用户 ID
- 集成 ID
- 是否使用 `Hub Key`
- 调用时间
- 本次扣减次数（默认固定为 `1`）

### 9.5 集成定义层

需要明确每个集成属于哪一类：

- 基础集成
- 高成本集成
- 是否支持 `Hub Key`
- 是否支持 `BYOK`
- 是否计入平台工具额度

当前基于已接入集成的建议分类如下：

#### 基础 / 用户自带凭据型

- Jira
- Confluence
- Splunk
- Elasticsearch
- Kibana
- AWS 全家桶相关集成

#### 平台托管高成本型

- AbuseIPDB
- Shodan
- VirusTotal

这层通常体现在各个 integration 的 `config.js` / 元数据中。

### 9.6 数据层

如果要真正做配额统计，后续可能需要新增或扩展数据库结构，用于记录：

- 哪个用户
- 调用了哪个集成
- 使用的是 `Hub Key` 还是 `BYOK`
- 消耗次数 / 消耗量
- 时间窗口内的累计用量

第一阶段工具调用统计建议直接落成：

- 每次调用一条记录
- `count = 1`
- 后续如果要支持不同工具不同权重，再扩展权重字段

### 9.7 Electron / Chat App 层

这层主要是消费 Hub 返回的能力结果：

- 自定义模型是否显示在 chat 模型选择器中
- 用户可安装 / 可配置哪些集成
- 是否给用户显示某些功能受套餐限制

当前共识下：

- Chat app 不需要单独定义一套新的套餐体系
- 它主要跟随 Hub 返回的权限与模型列表
- 其中“自定义模型是否出现”应由 Hub 权限结果决定

## 10. 当前优先级建议

建议按下面顺序推进：

1. 先统一 Billing 页面与套餐文案
2. 再统一 Hub 后端中的套餐权限映射
3. 然后做自定义模型的 `PRO / Enterprise` 限制
4. 然后补高成本集成的 Hub Key 配额系统（第一阶段按 `1 次调用 = 1 次额度`）
5. 最后再视真实使用情况决定是否引入加权工具计费
