# SaaS 定价规范

本文件作为 SaaS 套餐、模型额度、工具额度与按量付费的设计规范。

适用范围：

- `BASE` / `PRO` 两个 SaaS 套餐
- 平台托管模型：`medium`、`strong`
- 平台托管高成本工具：A / B / C 梯队

---

## 1. 设计原则

本产品的 SaaS 定价采用以下原则：

1. 订阅费购买“权限 + 月度体验额度”。
2. 高频使用成本不由固定套餐承担，而由用户按量购买承担。
3. 模型额度与工具额度分开，不混成同一个池子。
4. 所有免费或订阅附带额度一律按“月度”发放，不使用“日额度”。
5. `PRO` 的核心价值是解锁更强能力，同时提供更完整的体验。

---

## 2. 模型定义

模型映射：

- `medium` = `Claude Sonnet 4.6`
- `strong` = `Claude Opus 4.6`

模型成本口径：

| 模型 | 输入单价 | 输出单价 |
|------|---------|---------|
| `medium` | `$3 / MTok` | `$15 / MTok` |
| `strong` | `$5 / MTok` | `$25 / MTok` |

内部预算默认采用中位口径估算：

- 输入 / 输出按 `1:1` 估算

---

## 3. 模型计费规则

为了让产品更简单，模型侧统一采用：

- 单一 `token balance`
- 模型倍率扣费

倍率规则：

| 模型 | 扣费倍率 |
|------|---------|
| `medium` | `1x` |
| `strong` | `3x` |

含义：

- 用户请求 `medium` 时，按实际 token 消耗扣减
- 用户请求 `strong` 时，按实际 token 消耗的 `3 倍` 扣减

示例：

- `medium` 消耗 `100k tokens`，扣 `100k`
- `strong` 消耗 `100k tokens`，扣 `300k`

这条规则适用于：

- 月赠送额度
- 用户充值购买的 token

不再为 `strong` 单独建立一个固定赠送池。

---

## 4. 套餐规范

### 4.1 BASE

定位：

- 试用与轻度正式用户
- 只开放 `medium`
- 以体验产品为主

建议值：

| 项目 | 规范 |
|------|------|
| 月费 | `$0 ~ $9` |
| 可用模型 | `medium` |
| 月赠送 token | `2M` |
| `strong` | 不开放 |
| 自定义模型 | 不开放 |
| 工具额度 | `A: 500`, `B: 800`, `C: 1500` |

### 4.2 PRO

定位：

- 正式使用门槛
- 解锁 `strong`
- 解锁自定义模型
- 内置额度足够支持真实体验，但不覆盖持续高频成本

建议值：

| 项目 | 规范 |
|------|------|
| 月费 | `$29` |
| 可用模型 | `medium`, `strong` |
| 月赠送 token | `5M` |
| `strong` | 开放，按 `3x` 扣费 |
| 自定义模型 | 开放 |
| 工具额度 | `A: 2000`, `B: 3000`, `C: 5000` |

---

## 5. 月度额度规则

模型额度规则：

1. 所有套餐附带 token 均为“每月赠送额度”。
2. 不再使用“每日免费 token”。
3. 月度额度对试用用户更友好，也更利于产品体验。
4. 月度额度用完后，应继续允许用户通过充值使用，而不是直接阻断产品价值。

工具额度规则：

1. 工具额度同样按月发放。
2. A / B / C 梯队继续采用 `1 次调用 = 1 次额度`。
3. `BYOK` 不消耗平台工具额度。

---

## 6. 按量购买规范

### 6.1 token 包

token 包的职责：

- 承接超出月赠送额度后的使用
- 让高频用户自行承担真实模型成本
- 避免订阅费倒挂

建议包：

| 包名 | 价格 | token | 单价 |
|------|------|-------|------|
| Starter | `$10` | `2M` | `$5 / 1M` |
| Growth | `$30` | `7M` | `$4.29 / 1M` |
| Pro | `$80` | `20M` | `$4 / 1M` |

规则：

- 月赠送额度与充值 token 共用同一扣费逻辑
- `strong` 依旧按 `3x` 倍率消耗

### 6.2 工具额度包

工具侧保留分梯队售卖。

建议包：

| 包 | 价格建议 |
|----|---------|
| `A: 50 calls` | `$15` |
| `A: 200 calls` | `$50` |
| `B: 200 calls` | `$8` |
| `B: 1000 calls` | `$35` |
| `C: 1000 calls` | `$5` |
| `C: 5000 calls` | `$20` |

## 7. 内部核算与差价来源

本产品对外出售的不是 Claude 原始账单单位，而是平台内部的 `token balance / credit`。

对外规则：

- 用户看到统一的 token 余额
- `medium = 1x`
- `strong = 3x`
- 用户不直接感知 Claude 的原始 input / output / cache 账单结构

对内核算：

- 平台内部按真实模型成本核算
- 真实成本由以下几部分组成：
  - input tokens
  - output tokens
  - cache writes
  - cache hits / refreshes

当前第一阶段的产品定价，不单独向用户拆分 cache 收费，而是把 cache 作为平台内部优化收益处理。

当前差价和缓冲空间主要来自以下几部分：

1. `strong` 采用 `3x` 扣费，而不是按 Claude 原始成本 1:1 转售
2. `medium` 对用户按正常 token 消耗计价，不把 cache 命中的成本下降直接返还给用户
3. `PRO` 用户的月度赠送额度不会被所有人 100% 用满，未消耗额度会摊薄整体成本
4. 高频用户继续购买 token 包和工具额度包，用于回收持续使用成本

关于 `medium` 的产品定价，建议内部目标不要按 Claude 原始成本平卖，而应保留约 `1.2x` 左右的温和溢价，用于覆盖：

- 平台运维与工程成本
- 支付通道损耗
- 风控与滥用缓冲
- 价格波动和缓存命中率波动

## 8. 成本评估

### 8.1 BASE 成本评估

`BASE` 月赠送 `2M tokens`，全部按 `medium` 中位口径估算：

- `1M input + 1M output`
- 成本约：
  - 输入成本：`1M * $3 / MTok = $3`
  - 输出成本：`1M * $15 / MTok = $15`
  - 合计约 `$18 / month`

结论：

- `BASE` 已经不只是“点一下”的试用额度，而是能支持一次较完整体验
- 主要风险不在基础模型额度本身，而在高成本工具与高频滥用

### 8.2 PRO 成本评估

`PRO` 月赠送 `5M tokens`，如果全部按 `medium` 中位口径估算：

- `2.5M input + 2.5M output`
- 成本约：
  - 输入成本：`2.5M * $3 / MTok = $7.5`
  - 输出成本：`2.5M * $15 / MTok = $37.5`
  - 合计约 `$45 / month`

结论：

- `PRO` 在默认满额使用下会有明显成本暴露
- 本规范接受这种前期体验优先策略，后续通过续费、token 包和工具额度包回收

### 8.3 strong 成本控制

`strong` 使用 `3x` 倍率后：

- `PRO` 用户可以较自然地体验 `strong`
- 不会像 `1x` 那样直接暴露过高 Opus 成本
- 高频 `strong` 用户仍会更快耗尽余额并进入充值

这是本规范中控制高成本模型风险的核心手段。

| 项目 | BASE | PRO |
|------|------|-----|
| 月费 | `$0 ~ $9` | `$29` |
| 可用模型 | `medium` | `medium`, `strong` |
| 月赠送 token | `2M` | `5M` |

| `strong` 扣费倍率 | - | `3x` |
| 自定义模型 | 否 | 是 |
| 工具额度 A/B/C | `500 / 800 / 1500` | `2000 / 3000 / 5000` |
| 超额后 | 买 token 包 / 工具包 | 买 token 包 / 工具包 |

## 10. 价格配置策略

价格、额度包和倍率不应长期硬编码在代码中。

建议采用以下策略：

1. 默认值可以保留在代码常量中，作为兜底配置
2. 生产环境实际价格应支持通过环境变量覆盖
3. 中长期建议迁移到管理员后台 UI 或数据库配置，由管理员在线调整

推荐优先级：

- 第一阶段：代码默认值 + 环境变量覆盖
- 第二阶段：管理员后台 UI + 数据库存储

原因：

- 环境变量适合初期快速上线和低频调整
- 管理后台更适合后期做价格实验、活动价、区域价和临时调价
- 避免每次改价都重新发版

本规范建议：

- 套餐月费
- token 包价格
- 工具额度包价格
- `strong` 倍率
- A / B / C 梯队默认额度

都应设计为“可配置参数”，而不是永久写死。

---

## 11. 实施要求

后续代码与产品文案应遵循以下要求：

1. 把免费额度从“日额度”统一改成“月度赠送额度”。
2. `BASE` 只开放 `medium`。
3. `PRO` 开放 `medium + strong`。
4. `strong` 统一采用 `3x` 扣费倍率。
5. 模型与工具继续分池。
6. Billing 页面应清楚区分：
   - 套餐附带月额度
   - token 包
   - 工具额度包
7. 上线后需重点监控 A 梯队工具的真实成本与滥用情况，如成本压力过高，优先回调 A 梯队额度，而不是优先压缩模型体验。
8. 价格和额度相关参数应支持配置化，不应长期写死在代码中。

---

## 12. 结论

本产品的 SaaS 不采用“无限送量”路线，而采用：

- 月度体验额度
- 权限分层
- 高频使用按量付费

其中：

- `BASE` 负责让用户真正体验到产品价值
- `PRO` 负责提供更完整的模型与工具能力
- 高频成本主要由 token 包和工具额度包承担

这是当前阶段偏体验优先、前期允许小幅亏损、但仍保留后续回收路径的一版定价规范。
